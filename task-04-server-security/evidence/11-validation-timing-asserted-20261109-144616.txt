OBSERVATIONS & ANALYSIS
-------------------------------------------------------------------------------
1. ISOLATED SCHEMA VALIDATION OVERHEAD:
   The server-side measurement around schema.safeParse() demonstrates that Zod
   schema execution adds minimal CPU overhead (mean ~0.02 to 0.04 ms per request,
   representing tens of microseconds) for short string schemas.

2. TOTAL REQUEST TIME DIFFERENCES:
   Total request latency differences between the pre-Zod and post-Zod test runs
   reflect multiple system-level factors rather than schema execution alone:
   - Host CPU scheduling and thread execution across Argon2id worker lanes (p=4);
   - Operating system memory management and garbage collection timing;
   - SQLite file system write latency during transactional database inserts;
   - Express view compilation and template rendering variability.
   The schema execution itself accounts for only ~0.04 ms of the request.

3. THE CLASSROOM "2-3 SECOND DELAY" DISCUSSION:
   The assessment notes: "In class, validation added a noticeable two to three second
   delay on signup. Find your number and submit it. If your number is high, say what you
   think is causing it rather than accepting it."
   In our local tests, schema validation alone did not produce multi-second delays.
   Without access to the specific classroom implementation, potential hypotheses for
   unexpected multi-second delays in other setups include:
   - Synchronous network calls (such as DNS MX lookups or external breached-password APIs)
     invoked during request validation;
   - Cryptographic work factors configured far higher than necessary (e.g. excessive
     Argon2id time cost or memory allocation causing OS paging);
   - Synchronous disk I/O, database connection contention, or un-indexed queries on the hot path;
   - Re-compiling or dynamically loading heavy modules inside route callbacks.
