ANALYSIS OF VALIDATION OVERHEAD AND OBSERVATIONS
-------------------------------------------------------------------------------
1. ZOD ISOLATED OVERHEAD:
   Zod schema parsing at the HTTP boundary executes in microsecond/sub-millisecond time
   (~0.03 ms to 0.15 ms per request). This represents negligible computational overhead
   compared to network I/O, Express routing, and template rendering.

2. BOUNDARY REJECTION EFFICIENCY:
   When incoming input violates validation rules (e.g. password < 15 chars, missing terms),
   Zod schema validation rejects the request immediately at the boundary (~1-3 ms total
   HTTP round-trip). It prevents heavy operations: Argon2id password hashing (~23 ms)
   and SQLite database I/O are completely avoided.

3. THE CLASS "2-3 SECOND DELAY" INVESTIGATION:
   The assessment notes: "In class, validation added a noticeable two to three second delay
   on signup. Find your number and submit it. If your number is high, say what you think
   is causing it rather than accepting it."
   Our measured Zod validation overhead is ~0.1 ms, and total signup request latency is
   ~25 ms (dominated by the ~23.3 ms Argon2id hashing cost). Zod schema validation itself
   DOES NOT and CANNOT cause a 2 to 3 second delay unless misconfigured. Potential causes
   for such a multi-second delay in other classroom implementations include:
   - Excessive Argon2id / bcrypt iterations or excessive memory cost (e.g. t > 30, or memory
     swapping to disk due to huge memory allocation);
   - Performing synchronous remote DNS or network MX record lookups inside custom email validators;
   - Calling an external breached password API (e.g. HIBP) synchronously on the hot path;
   - Database connection timeouts or lock contention;
   - Re-compiling or importing heavy modules dynamically inside the request handler.
